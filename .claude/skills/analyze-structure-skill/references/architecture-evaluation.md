# 架构评估框架

## 概述

本框架提供系统化的架构评估方法，帮助识别架构优势、问题和改进机会。评估基于量化指标和定性分析，确保评估结果客观、可操作。

## 评估维度

### 1. 可维护性（Maintainability）

**定义**：代码易于理解、修改和扩展的程度。

**评估指标**：

| 指标 | 计算方法 | 健康范围 | 说明 |
|------|----------|----------|------|
| 模块职责清晰度 | 单一职责模块数 / 总模块数 | > 80% | 每个模块应有明确的单一职责 |
| 代码重复度 | 重复代码行数 / 总代码行数 | < 5% | 重复代码增加维护成本 |
| 文档覆盖率 | 有文档的模块数 / 总模块数 | > 60% | 关键模块应有文档 |
| 命名一致性 | 符合命名规范的符号数 / 总符号数 | > 90% | 一致的命名提高可读性 |

**评估方法**：

```bash
# 1. 模块职责分析
$CODEMAP query -m "<module>" -j | jq '.exports | length'
# 导出符号过多可能表示职责不单一

# 2. 代码重复检测
$CODEMAP complexity -j | jq '.[] | select(.duplications > 0)'

# 3. 文档覆盖率
$CODEMAP query -m "<module>" -j | jq '.has_docs'

# 4. 命名规范检查
$CODEMAP query -s "function" -j | jq '.[] | .name' | grep -E "^[a-z][a-zA-Z0-9]*$"
```

**改进建议**：
- 职责不单一的模块：拆分为多个模块
- 代码重复：提取为共享工具函数
- 缺少文档：补充 JSDoc/docstring
- 命名不一致：制定命名规范并重构

### 2. 可扩展性（Extensibility）

**定义**：系统易于添加新功能的程度。

**评估指标**：

| 指标 | 计算方法 | 健康范围 | 说明 |
|------|----------|----------|------|
| 插件化程度 | 支持插件的模块数 / 总模块数 | > 30% | 关键模块应支持扩展 |
| 配置灵活性 | 可配置项数 / 硬编码值数 | > 1.0 | 优先使用配置而非硬编码 |
| 接口抽象度 | 抽象接口数 / 具体实现数 | > 0.3 | 使用抽象降低耦合 |
| 新功能添加难度 | 新功能涉及模块数 | < 5 | 新功能应尽量局部化 |

**评估方法**：

```bash
# 1. 插件化分析
$CODEMAP query -S "plugin" -j | jq length
$CODEMAP query -S "extend" -j | jq length
$CODEMAP query -S "register" -j | jq length

# 2. 配置分析
$CODEMAP query -S "config" -j | jq length
$CODEMAP query -S "process.env" -j | jq length

# 3. 接口抽象分析
$CODEMAP query -S "interface" -j | jq length
$CODEMAP query -S "abstract" -j | jq length

# 4. 影响分析
$CODEMAP impact -f "<new-feature-file>" --transitive -j | jq length
```

**改进建议**：
- 缺少插件化：添加扩展点和钩子
- 硬编码过多：提取为配置文件
- 接口抽象不足：引入接口/抽象类
- 影响范围过大：重构降低耦合

### 3. 可测试性（Testability）

**定义**：代码易于测试的程度。

**评估指标**：

| 指标 | 计算方法 | 健康范围 | 说明 |
|------|----------|----------|------|
| 模块独立性 | 可独立测试的模块数 / 总模块数 | > 70% | 模块应尽量独立 |
| 依赖注入程度 | 使用 DI 的模块数 / 总模块数 | > 50% | 依赖注入提高可测试性 |
| 测试覆盖率 | 测试覆盖的代码行数 / 总代码行数 | > 70% | 关键代码应有测试 |
| 测试复杂度 | 测试文件平均复杂度 | < 10 | 测试应简单明了 |

**评估方法**：

```bash
# 1. 模块独立性
$CODEMAP deps -m "<module>" -j | jq '.dependencies | length'
# 依赖过多可能影响独立性

# 2. 依赖注入分析
$CODEMAP query -S "inject" -j | jq length
$CODEMAP query -S "constructor" -j | jq '.[] | select(.params | length > 0)'

# 3. 测试覆盖率
find . -name "*.test.*" -o -name "*.spec.*" | wc -l
find . -name "*.ts" -o -name "*.js" | wc -l

# 4. 测试复杂度
$CODEMAP complexity -f "src/**/*.test.ts" -j | jq '.[] | .complexity'
```

**改进建议**：
- 依赖过多：重构减少依赖，使用依赖注入
- 缺少 DI：引入依赖注入框架
- 覆盖率不足：补充单元测试和集成测试
- 测试复杂：简化测试，使用测试工具

### 4. 性能（Performance）

**定义**：系统执行效率和资源使用效率。

**评估指标**：

| 指标 | 计算方法 | 健康范围 | 说明 |
|------|----------|----------|------|
| 热点代码复杂度 | 热点文件平均复杂度 | < 15 | 热点代码应尽量简单 |
| 瓶颈模块依赖 | 瓶颈模块被依赖数 | < 10 | 瓶颈模块不应被过度依赖 |
| 资源消耗模式 | 识别资源密集型操作 | N/A | 标记需要优化的操作 |
| 缓存使用度 | 使用缓存的操作数 / 总操作数 | > 30% | 频繁操作应使用缓存 |

**评估方法**：

```bash
# 1. 热点代码识别
$CODEMAP complexity --top -l 10 -j | jq '.[] | {file, complexity}'

# 2. 瓶颈模块分析
$CODEMAP deps -j | jq '.[] | {module, dependents: .dependents | length}'

# 3. 资源密集型操作
$CODEMAP query -S "readFile" -j | jq length
$CODEMAP query -S "fetch" -j | jq length
$CODEMAP query -S "database" -j | jq length

# 4. 缓存使用分析
$CODEMAP query -S "cache" -j | jq length
$CODEMAP query -S "memoize" -j | jq length
```

**改进建议**：
- 热点代码复杂：重构简化
- 瓶颈模块：优化或拆分
- 资源密集型：添加缓存、异步处理
- 缺少缓存：引入缓存机制

## 综合评分

### 评分方法

每个维度评分 0-100，加权计算总分：

```
总分 = 可维护性 × 0.3 + 可扩展性 × 0.25 + 可测试性 × 0.25 + 性能 × 0.2
```

### 评分标准

| 评分 | 等级 | 说明 |
|------|------|------|
| 90-100 | 优秀 | 架构设计优秀，无需改进 |
| 80-89 | 良好 | 架构设计良好，少量改进 |
| 70-79 | 中等 | 架构设计一般，需要改进 |
| 60-69 | 较差 | 架构设计较差，需要重构 |
| < 60 | 差 | 架构设计差，需要重新设计 |

### 评分示例

```markdown
## 架构健康度评分

| 维度 | 评分 | 等级 | 关键问题 |
|------|------|------|----------|
| 可维护性 | 75 | 中等 | 模块职责不够清晰，代码重复度较高 |
| 可扩展性 | 65 | 较差 | 缺少插件化机制，硬编码较多 |
| 可测试性 | 80 | 良好 | 依赖注入较好，但测试覆盖率不足 |
| 性能 | 70 | 中等 | 存在热点代码，缺少缓存机制 |
| **总分** | **72.5** | **中等** | **需要重点改进可扩展性** |
```

## 问题识别

### 常见架构问题

#### 1. 循环依赖

**症状**：模块 A 依赖模块 B，模块 B 又依赖模块 A

**影响**：
- 增加编译/构建复杂度
- 难以独立测试
- 可能导致运行时错误

**检测**：
```bash
$CODEMAP cycles
```

**解决**：
- 引入中间模块打破循环
- 使用依赖倒置原则
- 重构共享代码到独立模块

#### 2. 上帝模块

**症状**：某个模块职责过多，代码量过大

**影响**：
- 难以理解和维护
- 修改风险高
- 测试困难

**检测**：
```bash
$CODEMAP complexity --top -l 5
$CODEMAP query -m "<module>" -j | jq '.exports | length'
```

**解决**：
- 按职责拆分为多个模块
- 提取公共功能到工具模块
- 引入门面模式简化接口

#### 3. 过度耦合

**症状**：模块间依赖过多，修改一个模块影响多个模块

**影响**：
- 修改风险高
- 难以独立开发
- 部署复杂

**检测**：
```bash
$CODEMAP deps -j | jq '.[] | {module, dependencies: .dependencies | length}'
$CODEMAP impact -f "<module>" --transitive -j | jq length
```

**解决**：
- 引入接口抽象
- 使用事件驱动架构
- 重构减少直接依赖

#### 4. 缺少抽象

**症状**：直接依赖具体实现，缺少接口或抽象类

**影响**：
- 难以替换实现
- 测试困难
- 扩展性差

**检测**：
```bash
$CODEMAP query -S "interface" -j | jq length
$CODEMAP query -S "abstract" -j | jq length
```

**解决**：
- 引入接口/抽象类
- 使用依赖注入
- 应用依赖倒置原则

## 改进路线图

### 短期改进（1-2 周）

1. **解决循环依赖**：打破所有循环依赖
2. **补充文档**：为核心模块添加文档
3. **统一命名**：制定并应用命名规范

### 中期改进（1-2 月）

1. **拆分上帝模块**：将大模块拆分为小模块
2. **引入接口抽象**：为关键模块定义接口
3. **补充测试**：提高测试覆盖率

### 长期改进（3-6 月）

1. **插件化改造**：为关键模块添加扩展点
2. **性能优化**：优化热点代码和瓶颈模块
3. **架构重构**：根据评估结果进行架构重构
